# DeepSeek 聊天网页技术观察

观察日期：2026-10-22（Asia/Shanghai）。目标：分析 `chat.deepseek.com` 的前端体验，为独立聊天客户端接入自定义 Base URL、API Key 和模型提供依据。

结论：可以独立实现接近的布局和交互。关键工作在消息渲染、流式状态、滚动与协议适配；修改官网某个 URL 不能直接得到支持任意中转站的客户端。

## 范围与证据等级

本次读取官网已登录首屏、DOM、公开发布的 JS/CSS 和静态资源响应头。未发送聊天消息，未执行官网私有接口，未读取认证存储，也未打开历史会话内容。项目当前尚未编写复刻实现。

- **页面实测**：首屏结构、编辑器元素、几何尺寸、DOM 节点数量。
- **静态确认**：发布包包含的库、逻辑及接口名称。代码存在不等于所有用户、所有页面和所有功能开关下都会执行。
- **设计建议**：独立客户端可以采用的实现方案，并非对 DeepSeek 内部架构的断言。

未捕获聊天网络请求或 SSE 响应，未录制 Performance trace，未做帧率、首字延迟、内存或长会话压测。因此本报告不声称测得具体性能，也不能确认流式播放观感的全部实现细节。

## 与流畅体验直接相关的实现

### 1. 消息列表支持可变高度虚拟化

业务消息列表接入虚拟列表组件，具有条目 key、估算高度、实际高度更新和 ResizeObserver 管理。实现还包含高度前缀和与位置查找逻辑。

这类设计让长对话无需始终挂载所有消息 DOM；公式、代码块和流式输出改变高度时，列表可以重新计算位置。实际是否启用虚拟化受运行时状态影响，需要在长会话中另行验证。

**复刻建议**：优先解决可变高度测量、稳定 message ID、滚动位置保持，再追求更复杂的虚拟列表算法。首版短对话也可以先使用普通列表，但应保留替换边界。

### 2. Markdown 更新会考虑渲染成本

Markdown 业务调用使用带耗时参数的内容更新辅助逻辑，依据前一次更新用时计算下一次可更新的时机，并设置计算等待值上限。生成状态会启用这一逻辑，渲染层还处理 AST、引用和输出预测相关状态。

这支持“接收频率与重渲染频率分离”的判断。它不意味着每个 token 都重跑整个页面，也不意味着固定等待两秒才显示文字；本次没有运行中的流式轨迹，不能确定具体视觉节奏。

**复刻建议**：流式数据先进入缓冲；分批更新正在生成的消息，缓存已完成的块，避免每个 chunk 都重新解析全部历史。公式和代码高亮应避免反复处理不完整内容。

### 3. 自动滚动有独立状态

代码区分用户滚动、请求跟随、强制到底及当前是否跟随；还有针对正在生成回复正文位置的计算。CSS 主消息列表关闭浏览器默认 overflow anchoring。

这说明它不是对所有内容变化一律调用 scrollIntoView。用户阅读上文和追踪新回复是两个需要协调的状态。精确触发阈值和交互效果仍应通过实际生成验证。

**复刻建议**：用户上滚后停止跟随，提供回到底部入口；流式增长、展开思考和延迟公式渲染时保持阅读锚点。侧栏滚动与消息滚动分别管理。

### 4. 重型功能分包

运行时存在按语言组拆分的 Prism 包，以及 KaTeX、Mermaid、预览等独立模块映射。公式逻辑还有 KaTeX 与另一 WASM 渲染器的回退路径。

这支持按需加载设计，但不能据分包映射断言所有模块直到首次点击才下载：例如本次首屏已经发现 KaTeX CSS。

发现的 Worker 构造调用位于挑战计算相关代码。本次证据不足以声称 Markdown 解析都运行在 Worker，或整站流畅主要依赖 WASM。

### 5. 输入框和微交互细节

输入框实际是 textarea，不是复杂富文本编辑器。具有自动高度相关测量、滚动容器处理，以及输入法 composition 状态管理，避免中文选词回车被当成发送。

本次桌面视口宽约 1482 CSS px：主区从 x=261 开始；欢迎区外层宽 840 px；输入卡宽 776 px、高约 124 px；textarea 内容区高 60 px。尺寸仅对应这次视口与状态。

CSS 中输入卡圆角为 24 px，常规动效变量为 200 ms，快慢分别为 100 / 300 ms；常规缓动为 cubic-bezier(.4, 0, .2, 1)。正文基础排版变量为 16 px / 28 px。样式涵盖透明度、位移、阴影和部分高度动画，不能概括成“只用合成层动画”。

侧栏首屏 DOM 含 100 个历史会话链接，总 DOM 元素约 1427 个。不能因为消息区有虚拟列表就认定侧栏也完全虚拟化。

## 流式与模型接入边界

公开代码包含 POST 请求、text/event-stream 检查、下载进度中的增量响应解析，以及 SSE 事件解析错误处理。这里不是只使用浏览器原生 EventSource：可见路径通过下载进度读取累积 responseText，再增量解析。

发现的聊天入口包括 completion、regenerate、continue、edit_message、resume_stream 和 stop_stream；会话列表、创建和历史消息另有接口。**这些是静态发布包中的路径，未调用，未验证当前服务器行为。**

官网协议还包含专有会话、消息和事件状态，不能把它视为任意第三方服务可直接替代的标准 API。

建议独立客户端按以下边界组织：

```text
页面：侧栏 / 消息列表 / 输入框 / 设置
                  ↓
本地会话、消息与生成状态
                  ↓
Provider 适配器：配置、能力、请求和流式解析
                  ↓
自定义中转站 Base URL + API Key + model
```

适配器可先支持常见的 chat-completions 风格协议，归一化为“开始、思考增量、正文增量、用量、完成、错误”事件。各中转站是否提供 reasoning_content、模型列表或其他参数，需要以其实际协议为准。任意 Base URL 不等于任意协议自动兼容。

API Key 不应编译到静态页面或进入源码。浏览器直连适合允许 CORS 的自用服务；若需服务端保管 Key、处理 CORS 或多设备配置，则增加自己的代理层。二者需要结合最终部署方式决定。

| 官网功能 | 自定义 API 能否直接获得 | 需要的工作 |
| --- | --- | --- |
| 文本对话、流式输出 | 通常可以，但取决于中转协议 | 请求与流式事件适配 |
| 深度思考展示 | 需要模型返回可展示的思考字段 | 模型选择、参数与展示能力映射 |
| 智能搜索及来源卡片 | 普通聊天接口不一定提供 | 搜索工具或专门服务、引用数据 |
| 文件问答 | 文本聊天接口本身不保证支持 | 文件解析、附件格式、检索与上下文 |
| 重试及编辑分支 | 可以由客户端组织 | 本地消息树与上下文构造 |
| 停止生成 | 客户端可中止接收 | 中止连接不保证上游计算及计费同时停止 |
| 断线恢复 | 依赖服务端支持 | 不能照搬官网恢复入口到普通中转站 |
| 历史、搜索、多端同步 | 是应用数据能力 | 本地数据库；多端同步另需后端 |

## 后续复刻建议

## 2026-10-22 二次可见界面取证

在已登录的原版网页端重新检查了首页、搜索层、账户菜单、系统设置和一条已有会话。与前述静态产物分析相比，本次补充了可见状态与入口关系：

| 区域 | 原版可见行为 | 客户端对齐策略 |
| --- | --- | --- |
| 首页顶栏 | 主区没有模型顶栏，中心只保留欢迎语和输入卡 | 空会话隐藏主区顶栏 |
| 侧栏搜索 | 左上角搜索图标打开居中搜索层，背景模糊，结果显示标题、摘要和时间 | 使用全局 `ConversationSearchDialog`，不在侧栏常驻输入框 |
| 新对话 | 白色胶囊按钮，显示 `Ctrl + J` | 侧栏按钮显示快捷键，保留本地会话创建逻辑 |
| 已有会话顶栏 | 顶部显示当前会话标题，右侧为分享入口 | 使用会话标题和分享占位入口 |
| 用户菜单 | 左下角头像、用户名、三点菜单；菜单包含系统设置和数据管理 | 账户菜单承载设置入口，配置仍保留本地服务商能力 |
| 系统设置 | 大弹窗，左侧导航，右侧内容，主题用三张选择卡 | 设置弹窗改为左侧导航布局，继续承载本地 Provider 配置 |
| 输入卡 | 深度思考、智能搜索在左；附件和发送在右 | 调整附件按钮顺序与首页宽度 |

这些结论来自当天实际可见页面，不代表官网私有接口或未来版本的永久规格。

推荐独立开发接近的交互与排版，先实现自定义 Base URL、Key、model、文本流式、Markdown / 代码 / 公式、本地历史及可靠滚动。

先确认三项产品决策：希望达到的视觉还原程度；个人本地使用还是部署网页并多端同步；首批中转站所支持的协议和模型。首版性能验收应包含生成时持续输入、长代码块、公式高度变化、上滚阅读、停止与错误恢复，而不是仅比较空白首页截图。

本次不建议把官网生产 JS 直接复制进独立项目：它与官网私有协议、环境和业务依赖耦合。应把观察所得转化成自己的组件和数据层。

# 2026-10-22 本轮实测补充
